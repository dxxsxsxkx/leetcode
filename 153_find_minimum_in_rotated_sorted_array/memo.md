# 153. Find Minimum in Rotated Sorted Array

## Step 1

条件を確認する。

- Rotation：配列の最後の要素を最初に持ってくる。
- 計算量の制約：$O(\log n)$
- `n == nums.length`：ローテーション回数は最大でも配列の要素数
- `1 <= n <= 5000`、`-5000 <= nums[i] <= 5000`
- 配列の要素は全て互いに異なる。

計算量の制約から二分探索を考える。`step1.cpp` に書いたコードで 30分ほどで accept。

- 最も小さい要素を `true`、それ以外を `false` で表す。元々の配列は `[true, false, ..., false]` で、ローテーションによって `[false, ..., true, ..., false]` となっている。
- 配列を区切って、`true` が含まれているもの部分のみを残していく。区切りには右開区間を用いる。`begin`, `end` として `[begin, end)` に `true` が含まれるようにする。
  - 不変条件：`begin <= true < end`
- 区切られた配列をどう見る？
  - ローテーションが行われている。ローテーション回数が配列の要素数と同じ場合を除き、単調増加列になっている部分配列に `true` は含まれていない。
    - 配列の要素はユニークなのでイコールは生じない
  - 左から見ていって、単調増加列になっていたら無視する。
    - ここは繰り返し行うので切り出す
    - 最初にこの操作を配列全体に対してかけておいて、単調増加だったら `nums[0]` を返すことにする？
      → 配列を区切るごとに掛けないといけない！すると配列を左から舐める作業がループの中で毎回入ってしまい、計算量が増えて $O(n \log n)$ になってしまう？
- エッジケースとしては空配列を考える。空配列の場合は `-1` でも返すか。

けど、よく考えるとこのコードが accept されたのは自分の意図とは違う。

- そもそもこのコードだと時間計算量が $O(n \log n)$ になる。
- 単調増加列が2つ並んだ場合、前側を捨てる実装になっている。これは正しいロジックだが、意図していたのとは違う...。
- 改めて整理する。
  - 最初の時点で配列全体が単調増加列の場合、最初の要素が最小値である。
  - ここから、適宜分割しながら進める。
    - 2つの部分配列のうち単調増加でない配列に最小値が含まれている。
    - 両方が単調増加になっている場合、右側の配列に最小値が含まれる（これはローテーションの回数の制約から言える）。

違う発想を考える。`step1_alt.cpp` に書いた。

- 不変条件はそのまま。
- 最小値とその右側の要素は常に配列の最後の要素より小さくなる。これを使うと、`nums[mid] > nums.back()` であれば最小値は右側の部分配列の中にあり、そうでなければ左側の中にあることに。
  - 比較対象をちゃんと固定してあげる必要がある。
